# BotArba — Telegram-бот финучёта ИП (Kaspi Pay через ApiPay)

Бот считает деньги на руках: **стартовая сумма + поступления от продаж через
ApiPay − расходы, внесённые вручную**. Об отдельных оплатах не пишет: одна
сводка вечером и баланс по кнопке.

MVP для одного владельца (1–2 пользователя). Без веб-интерфейса и без
бухгалтерии в налоговом смысле — только движение денег за день.

---

## Как это работает

```
Kaspi Pay ──оплата счёта──> ApiPay ──вебхук──> /webhook/apipay ──> operations
                                 └──GET /invoices (раз в час)──┘        │
                                                                        ▼
  кнопки «Баланс / Расход / История»  ────────────────────> баланс = Σ operations
                                                                        │
                                            21:00 Asia/Almaty ──────────┘
                                              вечерняя сводка
```

Баланс **не хранится числом**. Каждая цифра в интерфейсе — агрегат по таблице
`operations`. Так расхождение всегда можно найти и исправить отдельной
операцией, не переписывая историю.

## Интерфейс

Постоянная клавиатура: **Баланс**, **Расход**, **История**.

| Команда    | Что делает |
|------------|------------|
| `/start`   | Приветствие и ввод стартовой суммы при первом запуске |
| `/income`  | Ручное поступление — деньги, которых ApiPay не видит |
| `/correct` | Корректировка баланса отдельной операцией (`+50000` / `-50000`) |
| `/settings`| Текущее время сводки и время последней сверки с ApiPay |
| `/settime` | Сменить время сводки: `/settime 19:30`. Применяется сразу, без перезапуска |
| `/export`  | Выгрузить всё в Google Таблицы немедленно |
| `/whoami`  | Показать свой Telegram ID — им заполняется `OWNER_TELEGRAM_IDS` |

Меню команд бот регистрирует сам при старте — настраивать `/setcommands`
в BotFather не нужно.

## ⚠️ Что ApiPay видит, а что нет

Это главный риск проекта, и он проверен по [официальной спеке ApiPay](https://apipay.kz/openapi.json) (OpenAPI 2.1.0):

**Видит сразу.** Счета, выставленные через ApiPay — кабинетом, API-ключом,
подпиской или печатным QR. Они попадают в `GET /invoices` немедленно и
приходят вебхуком.

**Видит с задержкой.** Продажи, проведённые в приложении Kaspi Pay **мимо**
ApiPay — например другим кассиром. Спека прямо говорит: такие продажи
«подтягиваются из истории Kaspi: не мгновенно и не всегда полностью».
В списке они помечены `is_imported: true`, фильтр — `origin=kaspi`.

Отсюда два следствия в коде:

1. Сверка идёт с `origin=all`, а не только по счетам ApiPay — иначе продажи
   с кассы не попадали бы в баланс вообще.
2. Окно сверки — **2 дня** (`SYNC_WINDOW_DAYS`), а не текущий день.
   Подтянутая продажа датируется временем самой операции, то есть появляется
   внутри уже закрытого дня. Спека требует перезапрашивать окно, а не только
   новые записи.

**Не видит.** Переводы на карту, поступления из других банков и наличные.
Для них есть `/income` и `/correct` — операции помечаются `source=manual`,
так что в любой момент видно, какая часть выручки пришла не через Kaspi.

> Касса Kaspi и счета ApiPay — **разные леджеры**, и приравнивать их нельзя:
> это сказано в описании `GET /cashbox/reconciliation` дословно. Поэтому бот
> не пытается «сойтись» с итогом смены Kaspi, а считает только то, что видит.

## Локальный запуск

```bash
git clone https://github.com/adiletpn/BotArba.git
cd BotArba

python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt

cp .env.example .env
# впишите BOT_TOKEN; OWNER_TELEGRAM_IDS можно узнать командой /whoami
python -m app.main
```

Тесты:

```bash
pytest -q
```

Вебхук локально недоступен снаружи. Чтобы проверить оплату из песочницы,
поднимите туннель и укажите его адрес как `webhook_url` у ключа ApiPay:

```bash
cloudflared tunnel --url http://localhost:8080
# webhook_url = https://<выданный-домен>/webhook/apipay
```

## Деплой на Railway

1. **Подключите репозиторий.** New → Deploy from GitHub → `adiletpn/BotArba`.
   `railway.json` и `Procfile` уже в репозитории, настраивать сборку не нужно.

2. **Создайте том и смонтируйте его в `/data`.** Service → Settings → Volumes →
   Mount path `/data`.

   > 🔴 **Без тома база исчезает при каждом редеплое**, и критерий приёмки
   > «после перезапуска сервера баланс и история сохраняются» не выполняется.
   > Контейнерная файловая система на Railway эфемерна.

3. **Переменные окружения** (Service → Variables):

   ```
   BOT_TOKEN=...
   OWNER_TELEGRAM_IDS=...
   APIPAY_API_KEY=...
   APIPAY_WEBHOOK_SECRET=...
   DB_PATH=/data/botarba.db
   BACKUP_DIR=/data/backups
   APIPAY_SANDBOX=false
   ```

   `PORT` Railway подставляет сам — не задавайте его руками.

4. **Включите публичный домен.** Settings → Networking → Generate Domain.

5. **Укажите вебхук в ApiPay:** `https://<домен>.up.railway.app/webhook/apipay`,
   затем создайте секрет подписи и положите его в `APIPAY_WEBHOOK_SECRET`.

6. **Проверьте:** `curl https://<домен>.up.railway.app/health` → `{"status":"ok",...}`.

Бот работает на long polling, поэтому один процесс и `numReplicas: 1` —
обязательны: вторая реплика начала бы забирать те же апдейты Telegram.

## Проверка по критериям приёмки

Автотестами закрыто 6 критериев из 8 — `pytest -q`, 77 тестов:

| Критерий из ТЗ | Как проверено |
|----------------|---------------|
| Стартовая сумма 1 000 000 ₸, повторно не меняется | `tests/test_db_start_balance.py` |
| Оплата 190 000 ₸ из sandbox → баланс 1 190 000 ₸ | `tests/test_acceptance.py` |
| Повторный вебхук не удваивает сумму | `tests/test_acceptance.py` (3 доставки подряд) |
| Расход 100 000 ₸ → 1 090 000 ₸, «Отменить» → 1 190 000 ₸ | `tests/test_acceptance.py` |
| Посторонний получает отказ | `tests/test_whitelist.py` |
| После перезапуска баланс и история сохраняются | `tests/test_acceptance.py` (база переоткрывается) |
| Вечерняя сводка в 21:00 по Алматы | `tests/test_scheduler.py` — расписание; живая отправка вручную через `/settime` |
| Отдельных сообщений о каждой оплате нет | по построению: вебхук пишет в базу и не трогает `bot.send_message` |

Ручная проверка оплаты в песочнице:

```bash
# 1. Выставить счёт в песочнице через кабинет ApiPay
# 2. Отметить его оплаченным — придёт настоящий вебхук:
curl -X POST https://api.apipay.kz/api/v1/invoices/<ID>/simulate-status \
  -H "X-API-Key: $APIPAY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"status":"paid"}'
```

При этом в `.env` должно быть `APIPAY_SANDBOX=true`: в рабочем режиме бот
обязан отбрасывать события песочницы (требование спеки ApiPay).

### Решения, которые стоит знать до правок

**Суммы — целые тиыны** (1 ₸ = 100 тиын), нигде не float. ApiPay отдаёт суммы
строками `"190000.00"`, разбор идёт через `Decimal`. ТЗ разрешает тенге или
тиыны; выбраны тиыны, чтобы округление на входе не ломало инвариант
«баланс = Σ операций».

**Идемпотентность — на `UNIQUE(external_id)`**, а не на проверке в коде.
Повторный вебхук упирается в ограничение БД (`ON CONFLICT DO NOTHING`), и
удвоение невозможно даже при гонке двух одновременных доставок.

**У операции два времени.** `occurred_at` — когда деньги двинулись (`paid_at`
у ApiPay), `created_at` — когда мы об этом узнали. Сутки считаются по
`occurred_at`, поэтому продажа, подтянутая из истории Kaspi через три часа,
попадает в свой день, а не в текущий.

**Отмена — флаг `is_cancelled`**, строки не удаляются и суммы не правятся.
Срок кнопки «Отменить» проверяется на сервере по времени операции: кнопка в
старом сообщении остаётся нажимаемой сколько угодно.

**Доступ отзывается в обе стороны.** `OWNER_TELEGRAM_IDS` — источник истины:
кого в переменной нет, тот при следующем старте теряет доступ и перестаёт
получать вечернюю сводку. Строки в `users` при этом не удаляются (на них
ссылается `operations.created_by`), снимается `is_active` — история цела.
Так передача бота от разработчика владельцу сводится к правке переменной.

**Возвраты — отдельные операции** со знаком минус, они уменьшают поступления
за день, а не попадают в расходы. Вебхук пишет возврат по его `refund_id`,
часовая сверка — по накопленному `total_refunded`; оба ключа начинаются с
`refund:<invoice_id>:`, поэтому сверка видит записанное вебхуком и не задваивает.

## Выгрузка в Google Таблицы

Бот отправляет **полный снимок** базы в веб-приложение Apps Script внутри
вашей таблицы, скрипт перезаписывает два листа: «Операции» и «Сводка по дням».

Перезапись, а не добавление строк — сознательно. Операции меняются после
записи: расход отменяют кнопкой, возврат уменьшает поступление, продажа с
кассы Kaspi приходит задним числом и встаёт в середину уже выгруженного дня.
Точечные правки пришлось бы отслеживать; полная перезапись идемпотентна —
повторяй сколько угодно, таблица всегда равна базе.

Выгрузка не блокирует бота: хендлеры только поднимают флаг, отправляет
отдельная задача не чаще раза в 15 секунд. Если Google недоступен — бот
работает как обычно, база остаётся источником истины, выгрузка повторится.

## Бэкапы

Ежедневно в 03:30 по Алматы в `BACKUP_DIR`, через backup API SQLite (не `cp`:
при WAL часть транзакций лежит в `-wal`). Хранятся `BACKUP_KEEP_DAYS` дней.

> На Railway том не бэкапится сам. Чтобы копия переживала потерю тома,
> забирайте файлы наружу — например `railway run cat /data/backups/<файл>`
> по расписанию или отдельным заданием в S3.

## Открытые вопросы из ТЗ — что сделано и что ждёт ответа

| Вопрос | Статус |
|--------|--------|
| Все ли продажи идут через счета ApiPay? | **Частично закрыт кодом.** Сверка берёт `origin=all`, поэтому продажи с кассы Kaspi подтягиваются тоже — но с задержкой. Наличные и переводы на карту остаются за `/income` |
| Кто, кроме владельца, видит баланс? | **Ждёт ответа.** В схеме есть роль `viewer`, но прав она пока не ограничивает: все из `OWNER_TELEGRAM_IDS` получают `owner`. Разделение прав — отдельная задача на ~20 строк, делать её вслепую смысла нет |
| Нужна ли выгрузка в Excel / Google Sheets? | **Сделано.** Два листа в Google Таблицах: все операции и сводка по дням с балансом на конец каждого дня. Обновляется после каждой операции; `/export` — принудительно. Из Таблиц выгружается в Excel одним пунктом меню |
| Комиссия Kaspi — отдельной строкой или «грязными»? | **Сейчас «грязными».** Поступление пишется полной суммой счёта; комиссии ApiPay в вебхуке не отдаёт. Если нужна чистая выручка — нужен ответ, какой процент и с каких типов оплат |
| Устраивает ли 21:00? | **Закрыт.** Время лежит в таблице `settings` и меняется командой `/settime` на лету — ни редеплоя, ни перезапуска |

### Что стоит проверить на реальном аккаунте до приёмки

1. **Полнота выручки.** Проведите несколько продаж разными способами (счёт
   через ApiPay, QR на кассе, перевод на карту) и сверьте список
   `GET /invoices?origin=all` с кассовой сменой Kaspi. Так станет видно,
   какая доля денег реально доходит до бота сама.
2. **Задержка импорта.** Замерьте, через сколько продажа с кассы появляется
   в ApiPay. Если дольше двух суток — поднимите `SYNC_WINDOW_DAYS`.
3. **Возвраты.** Сделайте возврат в песочнице и убедитесь, что он уменьшает
   поступления за день, а не превращается в расход.
